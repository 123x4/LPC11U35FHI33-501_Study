从内存看一次 IO

从 Custom_Pointer_Init() 这一行出发，看“和电脑收发数据”在内存里到底是什么样：数据住在哪几块内存、谁把它从一块搬到另一块。地址全部来自 List/Sample.map 和第 11 课的存储地址分布。

1/5🧭 本质

在单片机里，IO 的本质就是数据在几块内存之间被复制：USB 硬件负责“电线 ↔ USB RAM”这一段，CPU 负责“USB RAM ↔ 普通 RAM”这一段。

内存地址谁能读写这次用到的
USB RAM（2 KB）0x2000 4000 起USB 硬件 + CPUEP4 OUT 缓冲 0x2000 4500（收 GUI 命令）、EP3 IN 缓冲 0x2000 4480（回给 GUI），各 64 字节
SRAM0（8 KB）0x1000 0000 起只有 CPUreceive_buff 0x1000 1650（64 字节）、usb_sendBuffer_p 0x1000 0410（4 字节）、gloabSetting 0x1000 1833（132 字节）
指针：一个存“地址”的变量。usb_sendBuffer_p 自己住在 0x1000 0410，占 4 字节，里面存的数是 0x1000 1650，也就是 receive_buff 的地址。通过它写数据，就是“先读出这个地址，再往那个地址写”。

3/5Custom_Pointer_Init() 这一行到底做了什么

void Custom_Pointer_Init(void)
{
	usb_sendBuffer_p = receive_buff;

}

编译后是 4 条指令（反汇编 output/Sample.axf）：

a244: ldr r1, [pc, #0x3dc]   ; r1 = 0x1000040C（custom.c 的 .data 区开头）
a246: ldr r0, [pc, #0x3d8]   ; r0 = 0x10001650（receive_buff 的地址）
a248: str r0, [r1, #0x4]     ; 把 0x10001650 写进 0x1000040C + 4 = 0x10000410
a24a: bx  lr                 ; 返回

custom.c 里有初值的全局变量被编译器排在一起（.data 区，从 0x1000040C 开始）：SaveDPIflag 0x40C、FlashData 0x40D、Check_mode_flag 0x40E，空 1 字节对齐，usb_sendBuffer_p 0x410、VecDst 0x414……（map 文件 1415~1420 行）。所以编译器用“.data 开头 + 4”来找它。没有复制任何缓冲区内容，只是让一个指针“指过去”。之后谁通过 usb_sendBuffer_p 写东西，写进去的都是 receive_buff 那 64 个字节。

为什么要这样：SRAM 只有 8 KB，收（GUI 命令）和发（DPI 通知）共用一块 64 字节，省下 64 字节。

4/5💡 想法上：共用缓冲区为什么现在没出事

安全的前提是“同一时刻只有一件事在用它”
收命令（PC_Communicate()）和发 DPI 通知（Custom_Set_DPI()）都在主循环里，一件做完才做下一件，所以它们不会同时用这 64 字节。
这个前提没有写在任何地方。哪天有人把收命令挪进 USB 中断里（为了响应更快，这很常见），中断可能在 Custom_Set_DPI() 写到一半时进来，把 receive_buff 改掉，GUI 就会收到一包拼坏的数据。
以后你看到“两个用途共用一块内存”，先找出它安全的前提，再想这个前提会不会被打破；能写进注释的，就写进注释。
另一个藏着的坑：发不出去也说“成功”
USB_AutoDelay_LoadInEP_Data()（usb.c:302）最多等 60 × 10 µs = 0.6 ms 让 EP3 空出来；等不到就直接放弃这包，但仍然返回 TRUE。电脑如果一直不来取 EP3（比如 GUI 没开），这些包都会悄悄丢掉。现在问题不大，因为没有 GUI 时本来就不需要通知；但你写自己的协议时要知道这一点。

5/5小测

记住：GUI 命令先由 USB 硬件放进 USB RAM 的 EP4 缓冲（0x2000 4500），CPU 在主循环里把它复制到 SRAM 的 receive_buff（0x1000 1650）处理；回复写在同一块 receive_buff 里，再由 CPU 复制到 EP3 缓冲（0x2000 4480），等电脑来取。usb_sendBuffer_p 只是一个指向 receive_buff 的指针。
