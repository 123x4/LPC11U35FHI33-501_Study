LPC_ADC->CR 是怎么来的：手册变成了代码

第 3 课说过，LPC_ADC->CR 就是地址 0x4001C000。这个名字定义在 inc/LPC11Uxx.h，它就是把手册里的寄存器总览表照抄成了 C 代码。对比一下：

📖 手册 Table 351 · 第 384 页 · ADC 寄存器总览（基地址 0x4001 C000）
NameAccessOffset
CRR/W0x000
GDRR/W0x004
--0x008 Reserved
INTENR/W0x00C
DR0~DR7R/W0x010~0x02C
STATRO0x030
/* inc/LPC11Uxx.h:259 */
typedef struct {
  __IO uint32_t CR;          // 0x4001C000
  __IO uint32_t GDR;         // 0x4001C004
  __I  uint32_t RESERVED0[1];// 0x008 空着
  __IO uint32_t INTEN;       // 0x4001C00C
  __I  uint32_t DR[8];       // 0x4001C010 起
  __I  uint32_t STAT;        // 0x4001C030
} LPC_ADC_Type;

/* inc/LPC11Uxx.h:620、687 */
#define LPC_ADC_BASE (0x4001C000)
#define LPC_ADC ((LPC_ADC_Type *) LPC_ADC_BASE)

结构体里每个成员 4 字节，按顺序排，正好和手册的偏移地址一一对应，连那个 “Reserved” 空位都留了。所以写 LPC_ADC->CR，编译器就去读写 0x4001C000。以后看到任何 LPC_XXX->YYY，都可以去手册对应章节的寄存器总览表里找 YYY。

这个头文件是芯片厂商提供的（⬜ 现成），不用改。__IO 表示能读能写，__I 表示只读，对应手册的 Access 列。

5/6板子开关：#if 决定哪些行算数

同一份代码要给好几块板子用。inc/my_board.h 开头有一排板子名字，只有一个没被注释掉：

//#define HAPTIC_V4
//#define P723_POC
#define IRPT_V4              ← 现在编译的是这块板（第 21 行）
//#define V4_HALL_HPTIC_V4

然后代码里到处是 #if (defined(IRPT_V4))：“如果立了 IRPT_V4 这个牌子，就编译下面这几行”。选一块板子，看 Device_Init() 里这几段哪些行会被编译：

注意：#if 是在电脑上编译的时候决定的，不是芯片运行时判断。被排除的行根本不会进入芯片。这和 C 语言里普通的 if 完全不同。

读代码的第一条规矩
看到一段代码，先往上找有没有包着它的 #if，确认它对 IRPT_V4 算不算数，再去读。很多“看不懂为什么这样写”的代码，其实根本没被编译。在 Keil 里，没被编译的行会显示成灰色。

本课新词

工程（.uvproj）Keil 的清单：编译哪些文件、用什么设置
#include把另一个文件（通常是 .h）原样抄进来
#define给一段文字起名字，编译时替换
#if / #elif / #else / #endif编译时的开关：决定哪些行算数
链接把各个 .c 编译出的 .o 拼成一个完整程序
