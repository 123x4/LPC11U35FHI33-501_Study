1/13🧭 本质：custom.c 是哪一层抽象

custom.c 是前人在“按键”和“USB 报告”之间加的一层抽象：键位映射层。

如果没有这一层，代码会写成“左键引脚是低电平 → 报告第 1 字节第 0 位置 1”，每个键的功能是写死的。有了这一层，读按键的代码只负责说“第 i 个键按下了”，至于它代表左键、Ctrl+C 还是音量+，去查一张表 key_function[i]。表能被 GUI 改，所以鼠标能“改键”。

一次按键穿过的各层（点一层看它是谁给的、给出了什么抽象）

custom.c 的另一半本质：设置就是一块结构体内存（gloabSetting，132 字节），它在 RAM 里的每个字节和 EEPROM 里的一模一样。“保存设置” = 整块复制到 EEPROM，“读回设置” = 整块复制回来。

这层抽象在哪里“漏”（下面各节会细讲）：
① RAM 里只放得下一套配置，“切换配置”全靠从 EEPROM 读，读的那句被注释后，切换就成了空话（第 9 节）；
② 为了让 RAM 和 EEPROM 字节对得上，用了 #pragma pack(1)，代价是数据不对齐，M0 要逐字节读写（第 4 节）；
③ 查表用的下标没检查范围，个别 id 会读到表外（问题清单）。

2/13先猜：要你设计一个能改键的鼠标

先别看代码。假设老板说：“做一个鼠标，每个键的功能都能在电脑上的软件里改，改完拔掉再插上还记得。”你需要哪些零件？先自己想一分钟，再一个个点开看前人是怎么做的。

零件 1：每个键一条“它代表什么”的记录

→ key_function[10]，每条 5 字节：第 1 字节 id 说明类别（鼠标键 / 键盘键 / 组合键 / 多媒体 / 特殊功能……），后 4 字节是参数。第 5 节。

零件 2：一个翻译器，按记录把按键变成 USB 报告

→ Custom_HandleKey() 加 6 个处理函数。每次有键变化就跑一遍。第 6 节有模拟器。

零件 3：存起来，开机读回

→ gloabSetting 整块和 EEPROM 对应，OperateFlash_Store_*() 存、OperateFlash_Read_*() 读。本项目把开机读回注释掉了，所以现在“拔掉再插上”记不住。第 7 节。

零件 4：让电脑上的软件能改它

→ 老 GUI 协议：命令 0x02 改一个键位、0x05 切配置、0x07 恢复默认……由 PC_Communicate() 分发。第 9 节。

零件 5：出厂默认值、一键恢复

→ Custom_DefineKey_Init()、Custom_Perform_Init() 等一组 Init 函数。

你可能没想到的：多套配置

→ 老产品支持 2 套配置（游戏 / 办公），用 currentMode 选。RAM 只放当前那套，另一套在 EEPROM 里。

你猜到的零件越多，说明你越接近“设计者的视角”。读别人的代码，本质上就是反推设计者当时要解决什么问题。

4/13它管的数据：gloabSetting 的 132 个字节

场景：鼠标要记住“每个键干什么、DPI 几档、回报率多少、灯怎么亮”。这些都放在一个全局变量里：GLOAB_SETTING_MODE_TYPE gloabSetting;（custom.c:19）。类型定义在 inc/Led_Effect_H/custom.h:84~164。

它分两半：前 3 个字节是全局（.setting），后 129 个字节是一套配置（.settingMode）。点下面的格子或色块看每个成员：

动手 · gloabSetting 在 RAM 里的样子（每格 1 字节，格子里是开机后的默认值）
为什么正好 129 字节、成员之间没有空隙？因为 inc/gloab.h:20 写了 #pragma pack(1)：让编译器把结构体成员一个挨一个排，不补空字节。正常情况下 UINT16 要放在偶数地址，编译器会在前面补空字节。
证据：反汇编 OperateFlash_Store_ModeSetting()，算地址时是“第几套 × 0x81”（0x81 = 129）。
好处：RAM 里的样子和 EEPROM 里的样子一模一样，可以整块复制。代价：Cortex-M0 不能读写没对齐的 2 字节 / 4 字节数据，编译器只好拆成一个字节一个字节地读写（map 文件里 custom.o 用到了 __aeabi_uread4，就是干这个的）。而且这个 #pragma 一直没有恢复，所有 include 了 gloab.h 的文件里的结构体都被压紧了。
RAM 里只放一套：配置有 MODE_NUM = 2 套，EEPROM 里两套都有（0x003 起第 0 套，0x084 起第 1 套，第 11 课），但 RAM 里的 .settingMode 只有一份，就是“当前那套”。切换配置 = 从 EEPROM 把另一套读进来。

动手 · 选一种键位设置，看 5 个字节怎么解释
联合体（union）：几种结构共用同一块内存，写的人和读的人约定好“这次按哪种结构读”。这里的约定就是 id：id 是 0xFD，就按 shortcut（修饰键 + 普通键）读；id 是 0xFE，就按 key（键码）读。

6/13按键线：Custom_HandleKey() 翻译模拟器

场景：你按下或松开任何一个键、转一下滚轮，button.c / scroll.c 就把 10 个位写进 wheel_button_status，Device_Pack()（device.c:566）调用 Custom_HandleKey(wheel_button_status, &报告指针)。它做 4 件事：

  1. 1
    和上次比，算出哪些位变了：button_wheel_changed = button_wheel ^ last_button_wheel_status
  2. 2
    10 个键位挨个看：变没变（key_changed）、现在是按着还是松着（key_status）、它的 id 属于哪一类（ClassKeyfunction()）
  3. 3
    按类别交给对应的处理函数，往三张临时报告里填字节：鼠标 8 字节、键盘 8 字节、多媒体 3 字节。每次调用都从全 0 开始重新填，所以“松开”不用专门处理：松开的键这次不填就行
  4. 4
    只有“这一类里有键变了”，才把那张临时报告复制出去，并在返回值里置位（MOUSE_KEY_REPORT = 1、KEYBOARD_KEY_REPORT = 2、MULTIMEDIA_KEY_REPORT = 4），之后 Device_Report() 按这些位发送

键位物理键功能（id）按着
返回值里的位Device_Report() 怎么发（device.c:668~727）
MULTIMEDIA（4）3 字节 [05, 用法低, 用法高] 从 EP1 发（报告 ID 5），再等 1 ms

8/13DPI 线：按 DPI 键时发生什么

默认第 9 个键位（DPI 键，PIO0_11）的 id 是 0xC1（CYCLE_DPI），属于“特殊功能”。完整调用链：

Custom_HandleKey()
 └ DealSpecialFunctionKey()        按下且变了 → case CYCLE_DPI
    └ Custom_Dpi_Deal(CYCLE_DPI)   dpi_gear++，超过 dpi_max 回到 0
       └ Custom_Set_DPI(gear, save=TRUE, send=TRUE, led=TRUE)
          ├ dpi_x = dpi_class[gear].dpi_x            取这一档的值
          ├ optical_double_flag = (dpi_x > 0x3E)     老传感器的“翻倍”标志
          ├ dpi_x = dpi_value_array[dpi_x - 2]       查老传感器的寄存器值表
          ├ optical_set_dpi(dpi_x)   ← 被 #if 关掉（custom.c:396~398）：IRPT_V4 不改传感器
          ├ save → OperateFlash_Store_ModeSetting()   ← 写 EEPROM 129 字节，每按一次写一次
          └ send → 64 字节 [04, 00, 当前配置, 档位, dpi_x 低, dpi_x 高, 0…] 从 EP3 发给 GUI
结论
按 DPI 键：档位变了、EEPROM 写了、GUI 收到通知了，只有传感器没变，一直是 PAW3950_Init() 设的 1600（PAW3950.c:398）。
默认 4 档的 dpi_x 是 0x04 / 0x08 / 0x10 / 0x18；按 dpi_value_array（optical_3325.c）从 RESOLUTION_200 开始每格 +100 推算，分别对应 400 / 800 / 1600 / 2400，和代码旁注释写的 800 / 1600 / 2400 / 2400 对不上。这张表是老传感器 3325 的，对 PAW3950 没意义。

9/13GUI 线：老 GUI 命令怎么改设置

场景：电脑上的 GUI 从厂商接口的 EP4 发 64 字节过来，主循环里的 PC_Communicate()（pc_communicate.c:882）按第 0 个字节分发。回复从 EP3 发回去（名字 EP_3_CUSTION_OUT 是反的，其实是 IN，第 10 课）。新协议也走这里：第 0 个字节是 0x55（TEST_CMD）的包，交给 Protocol_ProcessReceiveData()（my_protocol_mouse.c）。

命令处理函数和 custom.c 的关系现在的效果
0x01PC_Sync_To_Device()GUI 把整块设置原样写进 EEPROM；最后一包时调 Custom_Load_ModeSetting()EEPROM 写了，但 Custom_Load_ModeSetting() 不再读，RAM 不变
0x02PC_ModeSetting_To_Device()改一个键位：从 EEPROM 读第 N 套进 RAM → 改 key_function[i]（5 字节）→ 存回生效：RAM 被换成 EEPROM 里的第 N 套 + 新键位
0x04（Performance_Setting() 被注释）本来是 GUI 改 DPI / 回报率只记一个 test_mode，不改设置
0x05PC_Select_WorkingMode()改 currentMode，存全局，调 Custom_Load_ModeSetting()切不过去：编号改了，RAM 里还是原来那套
0x07Custom_Restore_Default()直接在 custom.c 里，按 buffer[1] 恢复：1 键位 / 2 性能 / 3 灯效 / 4 当前配置 / 5 全部生效（RAM 改成默认；1~3 还会存 EEPROM）
0x09Profile_Modify_Name()改 settingMode.name 并存生效
0x11Bootloadable_Load()在 custom.c 里：RAM 0x10001F00 写 0xAA → 软件复位 → 公司 bootloader 进升级模式生效，升级入口，不能删
0x55Protocol_ProcessReceiveData()新协议，和 custom.c 无关生效

10/13💡 想法上：从这个文件学到的做事方法

1. 函数名是一份合同，注释掉代码会让它“撒谎”
Custom_Load_ModeSetting() 叫“加载配置”，可加载的那句被注释了。调用它的 PC_Select_WorkingMode() 以为切换成功，还回复 GUI“切好了”。
以后你注释掉一行代码之前，先问一句：调用这个函数的人，还以为它在干什么？要么连调用一起改掉，要么改名，要么在函数头写清楚“现在不读了”。否则就是给后来的人埋了一个会撒谎的函数。
2. 读老代码，先找“它管什么数据”
custom.c 有 1171 行，看着吓人，其实只围着一块 132 字节的 gloabSetting 转：谁写它、谁读它、谁存它。先把数据画出来（第 4 节那张格子图），再看函数，比从第 1 行往下读快得多。这个方法对任何文件都适用：先找数据，再找动作。
3. 分清“好的抽象”和“混进来的杂事”
键位映射层是好设计：T1A 换了引脚，这一层完全不用动，button.c 照样只说“第 i 个键”。不好的地方是这个文件里还混进了 DPI 存储、固件升级入口（Bootloadable_Load()）、配置档切换，这些和“改键”没关系。整理代码时，先保护好的抽象，再把杂事搬走，顺序不能反。
